# Batch B verification

Tests run on 2026-09-09 using the rootless Docker daemon on this host. Each flavor uses an isolated project. Initial light-app data lived in tmpfs and was removed after testing. Further runs use disk-backed directories outside this repository because `/tmp` is a small tmpfs. Test secrets are generated locally and excluded from this repository. Runtime evidence in those directories includes Compose output, container states, logs and HTTP responses.

A passing startup requires `docker compose run --rm prepare`, then `docker compose up -d --wait`. Persistence checks stop the stack and run `up -d --wait` again with the same data and credentials. Initialization jobs must exit 0; long-running services must be healthy. HTTP redirects to setup or login are expected for fresh installations.

The DHI recipes retain upstream application images when the original recipe had no DHI replacement. This applies to Dockhand and its socket proxy, MeshCentral, Baserow, AppFlowy and MinIO, Zulip, and Stoat, Garage and LiveKit. Each DHI environment example names these exceptions.

MeshCentral's MongoDB, Stoat services without a health executable and Zulip's memcached receive a read-only BusyBox copied by prepare from its pinned image. The DHI recipe also copies that image's musl loader. This adds executable tools to otherwise shell-free runtimes. Listener checks prove local readiness; worker checks require an established database or broker connection. They do not prove that push notifications, scheduled tasks or voice calls complete successfully. Those functions need separate functional tests.

The first persistence experiment used `compose restart`, which restarted one-shot initialization jobs before their database was ready and caused transient connection errors. The final test procedure uses stop followed by up, preserving dependency ordering. Results from that first experiment do not establish clean restart behavior.

Dockhand first boot exposed an upstream migration probe that selects `drizzle.__drizzle_migrations` before it exists. The recipe now runs the exact packaged Drizzle PostgreSQL migrator against `/app/drizzle-pg` before starting the bootstrap server. It uses the application database role. The change does not precreate private migration tables or suppress PostgreSQL logging.

Final log scans for both flavors of Uptime Kuma, MeshCentral and Dockhand found zero structured error/fatal events and zero plaintext ERROR/FATAL lines. Their saved container-state records show every long-running service healthy and every initialization job exited 0.

Baserow's single export worker blocked minute email-summary tasks during the initial template import. When the backlog drained, its duplicate-task guard logged errors. Both recipes now configure two Celery workers so scheduled tasks can run while templates import. The final standard cold retest observed 2.08 GiB memory usage under the 3 GiB limit and 44 PIDs under the 300 limit. All 157 templates imported in 249 seconds for standard and 226 seconds for DHI.

Baserow's bundled Gunicorn 23 logged the Uvicorn worker's deliberate SIGTERM at ERROR severity after graceful shutdown. Both recipes now download the official Gunicorn 24.1.0 wheel on first startup, verify its SHA-256 checksum and bundled license, and cache it in `python-overrides`. The application mounts that directory read-only and selects the wheel through `PYTHONPATH`. The healthcheck verifies the imported version and path. Both flavors logged `Starting gunicorn 24.1.0` from the actual backend master on cold start and saved-data restart. The [24.1.0 release notes](https://github.com/benoitc/gunicorn/releases/tag/24.1.0) describe the SIGTERM severity correction. Remove this override once the pinned application image bundles the fix.

A deliberate stop still logs `Error while closing socket [Errno 9] Bad file descriptor` at INFO severity. This matches the open [Gunicorn/Uvicorn socket-close issue](https://github.com/benoitc/gunicorn/issues/3013). No log filters or vendor source edits hide it. Both saved-data restarts and row reads passed afterward, but a literal transcript containing no error wording is not achieved. Both final `result.json` files record exit 0 for configuration, preparation, startup, template import, account/data creation, stop/up and persisted login/row checks. The state snapshots show three healthy services and two successful initialization jobs per flavor. The standard `full-lifecycle.log` also includes the final shutdown. No ERROR/FATAL severity events or tracebacks were found in either final transcript. Test data and containers were removed afterward; logs and result files are kept outside this repository.

On 2026-09-09, the [official Docker Hub tag listing](https://hub.docker.com/v2/repositories/baserow/baserow/tags?page_size=25&ordering=last_updated) mapped both `latest` and `2.3.3` to the recipe's exact digest. The only newer build was `develop-latest`. The [supported-runtime page](https://baserow.io/docs/installation/supported) also lists 2.3.3. No newer stable upstream image was available to pick up the Gunicorn fix.

Stoat's worker checks match its pinned source: [crond opens MongoDB](https://github.com/stoatchat/stoatchat/blob/61fd13629f9fbf750139c8928f83750502428179/crates/daemons/crond/src/main.rs), and [pushd opens RabbitMQ consumers](https://github.com/stoatchat/stoatchat/blob/61fd13629f9fbf750139c8928f83750502428179/crates/daemons/pushd/src/main.rs). Their probes require established connections to those respective dependencies. They still cannot establish external notification delivery.

The Gunicorn wheel initializer also passed interrupted-write recovery in both flavors. The test extracted each recipe's actual Python initializer and ran it as UID 1000 with capabilities dropped in a cached Python helper. A pre-existing mode-0444 `.next` file reproduced `PermissionError` before the fix. Removing that stale temporary file before writing allowed the pinned download, checksum, license and import checks to finish. A second run reused the verified wheel. Logs and results are kept outside this repository; no Baserow runtime or dependency bytes changed.

MeshCentral's final live-listener retests passed in both flavors. The MongoDB probe rejects a stale Unix socket when TCP port 27017 is closed, accepts a live TCP listener, then fails again after that listener closes. Both cold starts and saved-data stop/up runs returned an authenticated administrator with full site rights and passed the application-account MongoDB ping. Both long-running services were healthy; database-init and account-init exited 0. Full lifecycle logs contain no MongoDB E/F events or plaintext ERROR/FATAL lines. The informational first-boot missing-root authentication and sessions-collection messages remain visible. Exact tested Compose and environment hashes, state summaries, probe results and full lifecycle logs are retained outside this repository. Test containers and runtime data were removed.
